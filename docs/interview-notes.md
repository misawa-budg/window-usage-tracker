# 面接で説明するための論点

## まず伝えること

Windowsの前面アプリとウィンドウ状態を記録し、自分の時間の使い方を振り返るローカルアプリ。C#で収集プロセスとWinUI 3の表示プロセスを分け、SQLiteを介して共有する。

「作業に集中していた時間」を正確に測るものではない。Activeは前面ウィンドウ、Runningは観測したウィンドウの状態をまとめた時間であり、無操作やウィンドウのないプロセスは別問題。

## 説明できる強みと根拠

| 説明の軸 | 実装上の判断 | 交換条件・注意点 |
| --- | --- | --- |
| 常駐部分と表示部分を分離 | CollectorはWin32イベントと低頻度の全列挙、Viewerは必要時だけ起動。SQLiteで共有 | GUIを閉じても収集継続。CPU低負荷を実測済みとはまだ言わない |
| 書込頻度とデータ消失を両立 | 状態区間とバッチ保存に、15秒のチェックポイントを追加 | 強制終了で全保存は保証しない。チェックポイントで行数は増える |
| プライバシーとデモの分離 | タイトルは既定で非保存。実DBと合成データDBを分け、DEMO表記 | ローカル平文DBで、暗号化ではない。過去のタイトルは自動消去しない |
| 測ってから性能改善 | 不要な集計を除去し、区間計算を境界走査へ変更。追加計測でXAML生成も改善 | SQL比較とUI比較の測定境界を分ける。ディスプレイ表示完了時刻までは測っていない |
| 異常系を検証できる分離 | 収集ループに時刻・セッション状態を注入。DBトリガーで保存失敗を再現 | 模擬試験と実際のスリープ/シャットダウン試験は別 |
| 表示名と識別子を分離 | `.exe` は凡例・行ラベル・選択欄では省略し、内部キーと詳細ツールチップは保持 | 表示名で集計・選択すると異なるアプリを混同するため、キーには使わない |

## 週表示の比較（2026-09-16）

Desktop版に対応するコミット `550b38f` のSQL・区間計算と、修正後の同じ部分を比較。ユーザーのDBをReadOnlyで読み、ローカル当日を含む7日・5,112区間で各3回測定した。DB内容は出力せず、件数と時間のみ記録した。

| 測定箇所 | 旧処理 | 修正後 |
| --- | --- | --- |
| 表示に使わないバケット集計 | 2,105 / 3,055 / 3,264 ms | 呼び出しを削除 |
| 表示用区間取得 | 172 / 116 / 99 ms（2クエリ） | 31 / 66 / 51 ms（1クエリ） |
| 週の描画モデル作成 | 76 / 68 / 84 ms | 58 / 43 / 50 ms |
| 上記の合計 | 2,352 / 3,240 / 3,447 ms | 89 / 109 / 101 ms |

主因は、使っていない集計の実行だった。まず不要な処理を除き、残る計算量を改善した。さらにアプリ選択肢の更新中にSelectionChangedが発火して週の行を二重生成する経路を抑制した。

この比較は.NET 10のコンソール計測器で、新旧の実ソースを同じSQLite依存で実行したもの。旧配布exe全体との比較ではない。各回で旧処理→新処理の順に実行しているため、DB/OSキャッシュの影響は排除していない。XAML要素生成、ブラシ生成、画面レイアウト・描画、初回アプリ起動は含まない。「UIが約30倍速くなった」とは言わない。

## まだ確認・判断が必要な点

1. Desktopの旧配布版にはコード修正は自動反映されない。面接で見せる実行ファイルがどの版か確認する。
2. 実機での新Collector開始/正常停止/再起動/二重起動、ロック/スリープ/復帰、ログオフ等の試験は未完了。定期保存の単体テストだけで「運用上の問題はすべて解決」とは言わない。
3. 長期DB容量・常駐CPU/メモリの計測、保存成功のheartbeat、保管期限、クリーンな別PCでの実行確認は残課題。
4. 多ウィンドウの集約はActive > Minimized > Open。なぜこの定義か、Open優先や「全ウィンドウが最小化」の定義に変えるなら何が変わるか説明する。
5. Active切替を完全な履歴として保証しない。イベントは再観測のきっかけで、連続通知はまとめる。見えない期間は利用時間に補完しない。
6. 非表示の旧UIは追加修正で整理済み。Sharedの古いバケット系API、自動CI、DST移行日の23/25時間対応は追加改善の候補。面接前に全面改修する必要はない。

追加のUI計測では5,142区間で、読込開始〜最初のRenderingコールバックが変更前1,370 / 2,089 / 2,640 ms、変更後143 / 132 / 78 ms。配置の負荷を削減し、visual treeは28,561から1,024要素になった。詳細・計測上の制約は [検証記録](verification.md#desktop実データでのui計測と整理2026-09-16追加) を参照。これは上の旧SQL比較とは別実験であり、最終表示完了や全PCの応答時間を保証する値ではない。

## LLM利用の説明

実装支援にLLMを多く使ったことを明示し、本人が実際に担った要件決定・レビュー・動作確認・改善判断を区別して話す。後から監査で見つけた設計を「最初から自分がすべて考えた」とは言わない。

強い説明は「生成されたコードを動かした」ではなく、「どんな問題を観測し、何を測り、どの変更を選び、どのテストで確かめ、何がまだ保証できないか」を自分の言葉で話せること。

## 状態定義をどう説明・再検討するか

### ウィンドウの状態と、アプリへの集約は別の問題

単一ウィンドウについては、OSから取れる情報に対応させる。Activeは実際のforeground、MinimizedはIsIconic、Openは追跡対象のうち前面でも最小化でもないウィンドウ。「見えている」「読んでいる」「集中している」までは判定しない。別ウィンドウに隠れていてもOpenになり得る。対象外フィルタを通ったウィンドウだけを扱い、全プロセスの実行時間は測らない。

根拠: [GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow)、[IsIconic](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-isiconic)。三分類は「OSから安定して観測でき、実装と意味を説明しやすい範囲に絞る」という現在の評価として妥当。ただし当初の選定理由を証明するものではない。

同じexeが複数のウィンドウを持つ場合、1つの状態へ畳むルールが別途必要になる。

| ウィンドウの組合せ | 現行Collector | Open優先案 |
| --- | --- | --- |
| Active + Open / Minimized | Active | Active |
| Open + Minimized（前面なし） | Minimized | Open |
| Minimizedのみ | Minimized | Minimized |

現行は `Active > Minimized > Open`。「最小化されているものが1つでもあれば重視する」という解釈はできるが、これが時間の振り返りに最適だという根拠はない。一般的な「アプリを開いている」の感覚には `Active > Open > Minimized`、つまり全追跡ウィンドウが最小化された場合だけMinimized、の方が説明しやすいと考える。これは提案であり、今回の性能修正では変更していない。

なおViewerは、同一exeの保存区間が重なっていた場合に `Active > Open > Minimized` で表示上の競合を解消する。Collectorの同時ウィンドウ集約とは入力も目的も違うが、異なる優先度は説明・保守上の負担になる。仕様を決めた後で揃えるか、別名の規則として明示したい。

保存時点でウィンドウ情報を1状態へ集約済みなので、あとからViewerの優先度だけを変えても過去の複数ウィンドウ状態は復元できない。変更時は適用開始時点を記録し、履歴を勝手に再解釈しない。exe名単位なので、同名exeの別パス・別プロセスも同じアプリとして扱う制約がある。

### Running・記録なしの意味

Runningは観測したActive/Open/Minimizedの区間を統合した表示で、独立したOS状態ではない。記録なしは「不使用」の証明ではなく、Collector停止・対象外・ロック等のため観測できなかった可能性がある。Activeの時間も、ユーザーが離席していれば作業時間とは一致しない。

## データはどう画面になるか

```text
Win32イベント → 再観測要求をキューへ → ウィンドウ列挙・除外・exe単位に集約
→ AppIntervalTrackerが状態の開始/終了を区間にする
→ チェックポイントとトランザクションでSQLiteへ保存
→ Viewerが表示期間と重なる区間をReadOnlyで取得
→ 期間外を切り落とす・重複を境界走査で解消
→ 時刻を横位置/幅、アプリや状態を色へ変換 → WinUIで描画
```

SQLの条件は `end > from AND start < to`。区間を半開区間 `[start, end)` と考えると、境界で接しただけのものを二重集計しない。幅の基本は `区間秒数 / 1日秒数 × トラック幅`、位置はその日の開始からの経過時間。例えば24時間を960単位に描くと、1時間は40単位、30分は20単位になる。実際の画面サイズにはViewboxで拡縮する。欠測は空白のまま残す。

一覧はActiveのアプリを色分けし、週の上位8アプリ以外をOtherにまとめる。Otherも時間を削除せず色の分類だけをまとめる。下段はRunningか状態詳細を表示する。UTCで保存しローカル時刻で表示するが、現在の日境界処理はDSTの23/25時間日に未対応。

今回、一覧の描画を「各区間にItemsControl・Border・ToolTipを作る」方式から、「色ごとに1つのPath、区間はRectangleGeometry」へ変更した。区間の小数座標は保持し、情報を間引かない。区間ごとの詳細はマウス位置から右端配列を二分探索して取得する。左右キーでも区間を選べる。下段のアプリ別描画は従来方式を維持しており、すべてのグラフを新方式に統一したわけではない。

## なぜこの技術スタックを維持するのか

これは当初の意思決定の再現ではなく、現状を見て説明できる採用理由と代替案の比較。

| 選択 | 今の要件に合う理由 | 代替・弱点 |
| --- | --- | --- |
| C# / .NET | Win32との相互運用、非同期処理、型・テスト基盤を同じ言語で扱える | C++でも可能だが管理すべき範囲が増える。C#でもP/Invokeの寿命・エラー処理は必要 |
| Win32イベント + 定期観測 | 切替を起点に記録し、通知漏れを低頻度の再走査で補う | 短周期ポーリングは実装が単純だが負荷と取り逃しの交換条件がある。現在も完全なイベント履歴ではない |
| Collector / Viewerの分離 | GUIを閉じても記録継続。描画の問題を収集から切り離す | 保存先解決・停止制御・配布が少し複雑になる |
| SQLite | ローカル完結、サーバー不要、トランザクションと期間検索を使える | JSONLは追記が単純だが期間検索・集計を自作する負担がある。クラウド同期や多数同時書込向けの設計ではない |
| WinUI 3 / XAML | Windowsネイティブの見た目・標準操作部品で作りたい要件に合う | WPFも有力。WinUIは配布・ビルド依存が複雑で、大量のXAML部品生成は今回のように重くなる |
| Sharedの純粋な区間計算 | OSやGUIを起動せず境界条件・重複をテストできる | Sharedに旧バケット系APIも残っており、責務整理は続けられる |

根拠: [SQLiteの用途](https://www.sqlite.org/whentouse.html)、[WinUI 3](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/)。選択全体は個人用Windowsアプリとして妥当だが、「唯一の最適解」「WinUIだから必ず高速」とは言わない。.NETのターゲットはCollectorが10、Shared/Viewerが8であり、全体が.NET 10に統一済みという説明も不正確。

面接では、例えば「最初は実現したい機能と見た目を決め、技術選定・実装にはLLMの提案を多く使いました。その後、状態の意味と欠測の扱い、保存失敗のテスト、週表示の性能を見直しています」と、自分が実際に確認できた範囲で説明する。計測や修正もLLM支援で進めたことを隠す必要はない。

## 画面共有前に自分で確認すること

- AppIntervalTrackerの状態遷移とチェックポイント処理を追える。
- WinEventHookPumpのコールバックを軽くする理由と、メッセージループ・デリゲート保持を説明できる。
- SQLが検索範囲と重なる区間を取得し、表示時に境界で切ることを説明できる。
- 保存失敗のテストを1つ実行し、「何を壊して何を確認しているか」を説明できる。
- デモデータだけで画面を開き、24h/1week、Running/State詳細を自分で切り替えられる。
- 「何が記録されないか」「突然電源が切れたらどうなるか」に誇張せず回答できる。
